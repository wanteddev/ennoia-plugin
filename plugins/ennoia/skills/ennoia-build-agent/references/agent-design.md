# 업무에 맞는 graph 설계

이 문서는 구조를 고르는 판단 기준이다. 지원 필드·구조 제약·테스트 가능 여부는 현재 MCP schema와 실제 검증 결과를 따른다. 기존 graph의 일부 수정에서는 관련 없는 구조를 재설계하지 않는다.

## 선택 기준

| 업무에서 필요한 동작 | 우선 검토할 구성 | 선택을 바꿀 근거 |
| --- | --- | --- |
| 하나의 역할이 답변·검색·도구 사용을 수행 | `agent` | 역할별 입력·산출물 또는 실행 순서를 분리해야 할 때만 노드를 늘린다. 일반 agent도 MCP·RAG 도구를 사용할 수 있다. |
| 정해진 도구를 정해진 입력으로 호출 | `mcp` | 어떤 도구를 쓸지 LLM이 결정해야 한다면 agent의 도구 설정을 검토한다. |
| 추출 → 검토 → 작성처럼 순서가 정해짐 | agent 직렬 연결 | 단계가 많다는 이유만으로 동적 라우터를 추가하지 않는다. |
| 자연어를 고정 범주로 분류해 한 경로 선택 | `classifier` | 이미 구조화된 값으로 판정할 수 있으면 `conditional`이 적합하다. |
| 값 비교·상태 갱신·제한된 재시도 | `conditional` / `setState` / `while` | 종료 조건, state 선언, `maxIterations`를 정한다. while 본문은 `parentId`로 묶으며 중첩하지 않는다. |
| 정해진 여러 역할 중 다음 담당자 또는 종료를 동적으로 선택 | `orchestrator` | 각 agent의 `metadata.description`에 맡길 업무와 산출물을 적는다. 정해진 순서로 모두 실행할 업무라면 직렬 연결을 사용한다. |
| 수행 중 계획을 조정하며 하위 역할에 작업을 분해·위임 | `superagent` | 별도 Deep Agent runtime과 위임 구조가 필요할 때 선택한다. 고정 승인·조건·반복 노드를 같은 graph에 섞을 수 없다. |
| 특정 지점에서 사용자 승인·거절에 따라 이동 | `userApproval` | 일반 graph의 승인 경로를 명시한다. 안전 테스트의 `needs_approval`는 전체 실행 성공이 아니다. |

사용자가 구조를 지정했다면 그 의도를 우선한다. 요구와 현재 지원 범위가 충돌하면 충돌하는 지점과 가능한 대안을 설명한다. 테스트하기 쉬운 구조로 임의 변경하지 않는다.

## 역할과 자원 배치

orchestrator는 연결된 agent의 이름·설명·prompt를 보고 다음 담당자를 고르며 결과 본문을 직접 종합하는 역할은 아니다. 하위 agent의 복귀 edge는 runtime이 구성한다. SuperAgent의 하위 agent 설명도 위임 기준이므로 단순한 이름 반복 대신 어떤 입력을 받아 무엇을 반환하는지 적는다. SuperAgent edge와 일반 graph edge의 의미를 섞지 않는다.

사내 문서 근거가 필요한 경우 발견된 RAG index와 준비 상태를 확인하고, 업무 시스템의 최신 값이 필요하면 MCP 도구의 계약·연결 상태를 확인한다. 자원이 존재한다는 이유만으로 모든 agent에 붙이지 않는다. 모델은 사용자가 지정한 값을 유지하고, 필요한 구조화 출력·RAG·도구 기능을 지원하는지 현재 discovery로 확인한다. 설명만으로 비용·속도·실행 성공을 보장하지 않는다.

## 설계의 완료 조건

선택한 구성으로 입력부터 최종 산출물까지 경로를 설명할 수 있어야 한다. 조건에 쓰는 값은 생산 노드의 출력 계약과 맞추고, 입력 부족·검색 결과 없음·도구 실패를 구분한다. 반복은 끝나는 조건과 상한을 함께 두며, 승인이 필요한 업무는 승인 지점을 보존한다. 이 내용은 불필요한 별도 승인 절차를 만들지 않고 요청된 작업 안에서 정한다.

현재 schema의 테스트 지원 여부와 실행 정책을 설계 단계에서도 확인한다. SuperAgent의 구조 검증·저장 가능과 안전 테스트 미지원은 별개다. `valid=true`만으로 결과 품질이나 runtime 실행 성공을 판단하지 않는다. 전체 graph 작성은 [데이터 전달과 예제](dataflow-examples.md)를 참고한다.
